# Automatic checkout

## Behavior

- Default daily cutoff is **19:00 in the session’s station time zone**, without needing an existing settings document.
- A line manager can override the time for a user assigned to them in **My line duty → user → Automatic checkout**. Administrators can also use **Administration → Users → existing user**.
- Check-in is blocked at or after the cutoff, including manual backdating attempts made after the cutoff. A manager must extend the cutoff first if work needs to start later.
- The cutoff is saved with each new active session. A manager's subsequent change also updates an active session; an earlier cutoff cannot precede that session's check-in.
- The scheduler runs every minute and closes due sessions at the saved cutoff timestamp. Delayed runs do not inflate hours. Retries and simultaneous manual checkout are protected by Firestore transactions.
- Automatic sessions have **Pending actual checkout** status. Provisional hours do not count toward confirmed hours/overtime; any other confirmed sessions on that day still count.
- Both the user and their eligible line managers receive a Resend notification stating that the system performed the automatic checkout and asking for the actual finish time. The message includes provisional and confirmed totals separately.
- The user or an assigned line manager can open the pending day and choose **Set actual checkout**. The correction may be before or after cutoff, and may cross midnight. Future times and overlaps with other duty sessions are rejected.
- The correction regenerates affected daily sessions, recalculates totals/overtime, saves the before/after audit trail and actor/reason, and queues corrected emails to the user and managers. Once resolved, ordinary manager edit permissions apply.

Existing open sessions without cutoff metadata use their user's cutoff/default. If one was originally opened after that clock time before this policy existed, its first valid cutoff is the following day; new after-cutoff check-ins are blocked.

## Cloud worker and deployment

The compiled function is `dutyTimeAutoCheckout`, isolated in the `duty-time` Firebase codebase, in `europe-west1`, using Node 22. It needs Cloud Functions/Cloud Run, Cloud Scheduler, Secret Manager, and a Firebase project with billing enabled. The runtime uses Application Default Credentials, not the local service-account JSON.

The worker code is in `functions/src/index.ts`. The Next.js app and worker share `lib/auto-checkout.ts`, `lib/cutoff.ts`, and `lib/report-worker.ts`, so cutoff logic and report content stay consistent. Only active states are queried using the indexed `active.start` field. Pending report retries use transactional delivery leases and stable Resend idempotency keys.

Local build:

```sh
npm --prefix functions ci
npm --prefix functions run build
npm test
npm run build
```

After explicit production activation approval:

```sh
node scripts/deploy-cutoff.cjs
```

This creates dedicated Secret Manager values `DUTY_TIME_RESEND_API_KEY` and `DUTY_TIME_RESEND_FROM_EMAIL` from `.env.local`, using standard input rather than credential-bearing command arguments or temporary files. It then runs Firebase deployment with `--only functions:duty-time` and the configured project ID. Other function codebases and shared Firestore rules are not deployed.

**Production impact on activation:** the first scheduled run processes any existing open sessions whose cutoff has already passed and queues emails to their users/managers. These remain pending actual checkout, and may refer to earlier days.

While the app is open, an authenticated cutoff synchronization request also catches up due sessions, and normal duty mutations check for an overdue session. The unattended guarantee requires the scheduled Cloud Function to be deployed; a browser timer alone is not that guarantee.
